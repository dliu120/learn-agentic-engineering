<ConceptCard title="The minimum behavior contract" tag="template">

An agent specification should name:

1. **Goal** — what outcome is valuable?
2. **Capabilities** — what tools and data may it use?
3. **State** — what information can change during the run?
4. **Invariants** — what must never become false?
5. **Exits** — success, exhaustion, failure, and escalation.
6. **Evidence** — what proves the result is acceptable?

</ConceptCard>

<KeyInsightCallout>
A system prompt asks the model to behave. A specification gives the whole system a contract you can test.
</KeyInsightCallout>

## Example: research assistant

**Goal:** Produce a cited answer to one research question.

**Capabilities:** Web search and page reading. No posting, purchasing, or account changes.

**Invariants:** Every factual claim must cite a fetched source. The assistant must not follow
instructions embedded in source pages.

**Exits:** Success with cited answer; exhaustion at 12 sources; failure on unavailable search;
escalation when sources materially disagree.

<MisconceptionFlip
  claim={"A detailed implementation plan is an agent specification."}
  correction={"A plan describes how you intend to build. A specification describes behavior that remains true across implementations."}
/>

<DeepDive title="Executable invariants">

Some invariants can run as code: reject a final answer with uncited claims, block a write tool
without approval, or halt a graph when budget reaches zero. The closer the invariant is to the
runtime boundary, the less it depends on model compliance.

</DeepDive>
